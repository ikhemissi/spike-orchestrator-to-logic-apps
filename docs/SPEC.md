# Specification — Orchestrator → Logic Apps Standard migration spike

> **How this spec maps onto this repository** (these adaptations win over the text below):
> - **Layout:** one Terraform root in `infra/`, one file per part (`network.tf`, `vms.tf`, `automation.tf`, `logicapp.tf`, `alerts.tf`, …) calling modules of `infra/modules/` where one fits; the shared files from building blocks (`main.tf`, `providers.tf`, `monitoring.tf`, `key-vault.tf`, `network.tf` header comments, `infra/hooks/run.sh`, `infra/modules/*`) stay as they are. Wherever §4 says `infra/modules/<x>/`, write `infra/<x>.tf` (a new module only for a reusable concern).
> - **azd hooks:** azd runs `infra/hooks/run.sh <event>`, which runs `infra/hooks/<event>/NN-<name>.sh` in name order. The spec's `scripts/postprovision.*` and `scripts/postdeploy.*` become steps there (bash). Every script in `scripts/` has a bash **and** a PowerShell 7 version with the same behaviour.
> - **Names and tags:** resource group `rg-<env>`, names `<type>-<env>-<suffix>` from the locals of `infra/main.tf`; tags come from `local.tags` (the `RESOURCE_TAGS` azd value plus `azd-env-name`); add `workload = "orchestrator-to-logic-apps"` to them. Tenant-specific tags are set in the azd environment, never in files.
> - **Settings:** every Terraform variable is mapped in `infra/main.tfvars.json` from an azd value; azd passes strings, so declare precise types or resolve defaults in `locals` with `coalesce`.
> - **Documents:** `docs/DEMO-SCRIPT.md` is [docs/DEMO-RUNBOOK.md](DEMO-RUNBOOK.md); VERIFY outcomes are numbered experiments in [docs/experiments/](experiments/) summarized in `docs/DECISIONS.md`; the questions are in [docs/QUESTIONS.md](QUESTIONS.md).
> - **Public repository:** state VERIFY outcomes as dated, factual observations with neutral guidance.

## 0. Your mission

You are building a **self-contained, reproducible technical spike** in Azure that demonstrates how a set of System Center Orchestrator 2019 jobs can be migrated to **Azure Logic Apps Standard**, including the jobs that must keep using resources in an on-premises datacenter.

The spike will be shown live during a one-day architecture workshop. It must:

1. Deploy end-to-end from an empty subscription with **Terraform** (infrastructure) and **azd** (application/workflow deployment), plus a few helper scripts.
2. Implement **four business workflows + one child workflow + one diagnostic workflow** described in §5.
3. Simulate the "on-premises datacenter" and the "external partners" inside Azure (§3).
4. Ship **test data, seeding scripts, and an automated test runner** that proves each scenario, including **injected failures** (§7, §8).
5. Ship **monitoring and alerts** (§6).
6. Be torn down with a single command.

Work iteratively: build the foundation first, then one workflow at a time, test each before moving on. Do not stop at scaffolding — every workflow must actually run successfully against the simulated environment.

### Rules of engagement

- **Verify before you write.** Where this prompt says **VERIFY**, check the current Microsoft Learn documentation / Terraform provider docs / connector reference before implementing. Do not invent connector operation names, Terraform arguments, or API versions. If something does not exist, implement the documented fallback given here and record the deviation in `docs/DECISIONS.md`.
- **No secrets in Git.** All secrets are generated by Terraform (`random_password`, `tls_private_key`) and stored in Key Vault. The Logic App reads them via Key Vault references.
- **Everything parameterized.** No hard-coded hostnames, paths, IPs, or names in workflow definitions — use `parameters.json` backed by app settings.
- **Idempotency is a requirement**, not a nice-to-have: re-running any workflow or the runbook must never duplicate or resend a file.
- Keep a `docs/DECISIONS.md` log of every choice and deviation, and a `docs/DEMO-SCRIPT.md` (see §10).

## 1. Context (why this exists)

A typical estate this spike represents: ~50 Orchestrator jobs: ~95% scheduled, ~5% folder-monitoring. Jobs use native Orchestrator activities and PowerShell, call WinSCP for FTP/SFTP file transfer, call a local encryption tool, read/write NAS (SMB) shares, and move files to SharePoint Online. Failures are reported today by e-mails sent by the scripts themselves. Fewer than 10 jobs are critical; they must complete **within the day**, not within the minute. Datacenter ↔ Azure connectivity already exists (VPN/ExpressRoute). On-prem servers are Azure Arc-enabled.

Target design — each job step is classified into one of four patterns:

| Pattern | Meaning | Agent on-prem? |
|---|---|---|
| **P0 – Cloud only** | Logic Apps + built-in connectors (FTP, SFTP, Blob, HTTP/Graph) | No |
| **P1 – Agentless hybrid** | Logic Apps Standard reaches the NAS directly through VNet integration + VPN/ER using the **built-in File System connector** | No |
| **P2 – Data gateway** | Managed connector through the on-premises data gateway — **fallback only, NOT built in this spike** | Yes |
| **P3 – Hybrid worker** | Logic Apps starts an **Azure Automation** PowerShell runbook that runs on a **Hybrid Runbook Worker** in the datacenter (local tools such as encryption) | Yes |

The spike implements four representative jobs:

| ID | Job | Pattern |
|---|---|---|
| J1 | Get a file from an external partner FTP and send it to another partner's SFTP | P0 |
| J2 | Get files from an external FTP and upload them to SharePoint Online | P0 |
| J3 | Take on-prem files, encrypt them with a local tool, drop them in another NAS folder | P3 |
| J4 | Get files via FTP, then move them by type to NAS folders | P0 + P1 |

## 5. Workflows — detailed specification

### 5.0 Conventions for all workflows

- **Stateful.**
- First action: `Init_CorrelationId` = `guid()` (or reuse `triggerOutputs()?['headers']?['x-correlation-id']` when called by HTTP).
- **Tracked properties** on key actions: `correlationId`, `jobName` (e.g. `J1`), `fileName`, `partner`, `pattern` (`P0`/`P1`/`P3`), `outcome`.
- Structure: `Scope_Try` → `Scope_Catch` (runAfter `Scope_Try` = Failed, TimedOut, Skipped) → `Scope_Finally` (runAfter Succeeded, Failed, TimedOut, Skipped).
  - `Scope_Catch`: collect failed action details with `result('Scope_Try')` filtered on `status == 'Failed'`, call child `wf-child-run-report` with `outcome=Failed`, then **`Terminate` with status `Failed`** and a meaningful code/message (so the run is visibly failed and alerting works).
  - `Scope_Finally` (only on success path): call child `wf-child-run-report` with `outcome=Succeeded` and counts.
- Retry policy on connector actions: exponential, count 4, interval PT15S, max PT5M. No retries on `Terminate` or on idempotency checks.
- `For_each` loops processing files: **concurrency = 1** (sequential) to keep idempotency simple and avoid Automation job bursts.
- Trigger concurrency: **singleton** (`runtimeConfiguration.concurrency.runs = 1`) so two scheduled runs never overlap.
- Recurrence triggers: interval from parameter (`@parameters('j1RecurrenceMinutes')`, default 15 for the demo), `timeZone: "Romance Standard Time"`. Also each workflow must be **manually triggerable** by the test runner (the Recurrence trigger can be fired via the management API `.../triggers/<name>/run` — **VERIFY**; if not possible, add a second workflow variant or an HTTP-request trigger guarded by SAS — document the choice).
- All hosts/paths/accounts come from `parameters.json`, which references app settings (`@appsetting('...')`); secrets via Key Vault references in app settings.

### 5.2 `wf-j1-partner-ftp-to-sftp` — J1, pattern P0

Business meaning: partner A drops CSV files on its FTP server; they must be delivered to partner B's SFTP server; partner B allow-lists our source IP.

Trigger: Recurrence (parameterized).

Steps inside `Scope_Try`:
1. **FTP – List files in folder** `/outbound/j1` (connection `ftpPartnerA`).
2. **Filter array**: keep only files (not folders) matching `*.csv` and **not** starting with `~` or ending with `.partial`.
3. If none → Compose "no file", go to Finally with `filesProcessed=0` (a run with no files is a **success**).
4. **For each file** (concurrency 1):
   1. **FTP – Get file content** (`/outbound/j1/<name>`).
   2. **SFTP – Get file metadata** `/inbound/<name>` — configure this action's runAfter handling so that "not found" is treated as "does not exist" (do not fail the run).
   3. **Condition – already delivered?** If the target exists **and** its size equals the source size → mark `skipped-duplicate`, go to step 6.
   4. **SFTP – Upload/Create file** `/inbound/<name>.partial`, then **SFTP – Rename file** to `/inbound/<name>` (atomic delivery). **VERIFY** that the built-in SFTP connector has a rename operation; if not, upload directly to the final name and document this.
   5. Append `{name, sizeBytes, result:'delivered'}` to an array variable.
   6. **FTP – Move/Rename file** source to `/outbound/archive/<yyyyMMdd-HHmmss>_<name>` (or copy + delete if move is not supported — **VERIFY**). This is what makes a re-run safe.
5. Compose summary `{correlationId, job:'J1', filesProcessed, filesSkipped, files:[...]}`.

Failure behaviours to show (§8): partner B rejects us (IP not allow-listed) → SFTP action fails after retries → Catch → run Failed → alert.

### 5.9 Runbook `Invoke-EncryptAndMove.ps1` (PowerShell 7.4) — contract

Parameters: `CorrelationId` (mandatory), `SourcePath`, `TargetPath`, `ArchivePath`, `Recipient`, `MaxFiles` (default 100), `SimulateFailure` (switch, default off).

Behaviour:
- `$ErrorActionPreference = 'Stop'`. Log progress with `Write-Verbose -Verbose` / `Write-Information` — **never** `Write-Output` except for the single final JSON (anything else pollutes the output parsed by Logic Apps).
- **Fatal errors** (source path not reachable, `gpg` not installed, access denied on the share) → `throw` → job ends **Failed**.
- For each file in `SourcePath` (up to `MaxFiles`, ordered by name):
  - If the name contains `FAIL` **or** `SimulateFailure` is set → record a per-file error `SIMULATED_FAILURE` and continue (no throw) — this is the data-driven fault injection.
  - Compute SHA-256 of the source.
  - Target = `<TargetPath>\<name>.gpg`. **Idempotency:** if the target already exists **and** a sidecar `<name>.gpg.sha256` contains the same source hash → `skipped`, move the source to archive, continue.
  - `gpg --batch --yes --trust-model always --recipient <Recipient> --output <tmp> --encrypt <source>`, then rename tmp → target (atomic), write the sidecar hash file, move the source to `ArchivePath\<yyyyMMdd-HHmmss>_<name>`.
- At the end, emit **exactly one** `Write-Output` with compressed JSON:

```json
{
  "correlationId": "…",
  "status": "Succeeded | PartialFailure",
  "worker": "<COMPUTERNAME>",
  "runAs": "<whoami>",
  "filesProcessed": 0,
  "filesSkipped": 0,
  "filesFailed": 0,
  "items": [ { "name": "…", "result": "encrypted|skipped|failed", "sha256": "…", "error": null } ],
  "errors": [ { "code": "…", "message": "…", "file": "…" } ],
  "startedAt": "ISO-8601",
  "completedAt": "ISO-8601"
}
```

- Keep the output well under 1 MiB (no file contents, cap `items` at `MaxFiles`).
- Include `runAs` so the demo can show the job runs as `hw01\svc-azauto` and **not** as `NT AUTHORITY\SYSTEM`.
- Pester tests in `src/runbooks/tests/` run locally against temp folders (gpg mocked or real if installed).

## 9. Security checklist (must be true at the end)

- No secret in Git, in workflow definitions, or in run history: mark actions handling passwords/keys/file contents with **secure inputs/outputs** (`runtimeConfiguration.secureData`) where relevant.
- Logic App uses **only** managed identity + Key Vault references; no SAS keys or connection strings for Azure resources the identity can reach.
- Least privilege: `svc-la` only on `j4\*` and `folderwatch\*`; `svc-azauto` only on `j3\*`.
- Partner VM reachable only from the NAT IP and the deployer IP.
- Jobs cannot run in the Automation cloud sandbox (policy) — or the deviation is documented.
